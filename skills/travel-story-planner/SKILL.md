# Travel Story 旅行规划

## 应用调用方式

本 Skill 通过客户端已接入的 **Travel Story MCP 工具**完成行程操作。完整计划直接用 `apply_plan`，参数见 [工具速查与完整调用例](references/mcp-quickstart.md)；创建和录入的方式已在其中给出，无需自行研究实现。

此规则适用于全过程：检查、搜索、创建、修改和播放。旅行规划任务中，不读取 `app/api/**/route.ts`、服务端源码或数据库来推断调用方式，不用 curl/fetch/自写脚本直接访问 Travel Story HTTP API 代替 MCP，也不直接写行程文件。HTTP API 能响应不代表客户端已接入 MCP。工具缺失时按接入流程处理；只缺 `apply_plan/get_plan_task` 时说明工具版本未更新，请更新服务并重连，不回退 HTTP API 或逐地点重录。参数不清楚先看本 Skill 的速查及客户端工具 schema，校验失败按错误修正参数。只有用户另行明确要求开发或排查项目代码时，才进入源码调查。

`get_status.compatibility.status` 必须为 `compatible`，且 capabilities 包含 `planTasks/searchActivity/planReview:true`。`restart_required`、`SERVICE_VERSION_MISMATCH` 或 `UNKNOWN_TOOL` 表示运行版本不匹配：停止写入，说明需重启更新后的网页服务并重连 MCP；ensure_service 不能升级旧进程。不能把错误当作改用 create_trip/edit_itinerary、HTTP 或浏览器表单重录的理由。工具调用的外层 status:success 不代表业务成功，必须读取返回中的 isError/error。

## 必须遵守的执行顺序

**先检查服务，未启动就调用 `ensure_service({})`；服务就绪后必须实际打开 Agent 内置浏览器，确认页面已渲染且连接就绪，之后才允许录入。第一阶段完成后，同一轮直接录入并展示首版，不等待用户再说“展示”。**

**服务检查的第一个动作是调用已接入的 `get_status({})`，不先寻找项目目录、读取 setup.md/README、查看源码或研究启动命令。** 正常在线时直接复用返回的 URL 打开内置浏览器。仅 `SERVICE_UNAVAILABLE` 时调用 `ensure_service({})`，随后取状态并打开页面。搜索 Key 从状态返回值判断；只有缺少目的地所需 Key 或实际鉴权/配额错误时才读 [Key 配置说明](references/setup.md)。如果客户端未暴露 Travel Story 工具，只按客户端能力定向发现一次；仍无工具则明确 MCP 未接入，进入 [接入说明](references/mcp-execution.md#0-先检查服务再打开浏览器最后允许录入)，不把搜索项目源码当作服务检查。

1. **服务 → 浏览器 → 连接 → 录入，顺序不可跳过**：直接 `get_status({})` 检查服务；未启动调用 `ensure_service({})`，等待就绪后取一次状态。复用返回的 url/search/views，不重复预检。随后必须用 Agent 内置交互浏览器实际打开应用，快照确认真实 UI，再按需调用 `get_view_state({})` 更新并确认本次页面的 `viewId`、就绪状态和新鲜心跳。浏览器不存在/确实受限时才降级系统浏览器，仍须打开并验证页面。详细回执和异常处理按需读取 [MCP 执行参考](references/mcp-execution.md#0-先检查服务再打开浏览器最后允许录入)。**服务在线不等于页面打开，connectedViews 大于0也不等于本次内置页面就绪；未通过页面门槛，禁止 create_trip/edit_itinerary 等写入、后台录入或“先保存后打开”。**
2. **首版通过规划检查后继续展示**：已有实际日期、每日有序地点和交通，并通过§5的区域、时间、体力及依据检查，才是第一阶段完成。用户说“确认”不替代可行性检查；发现超时、关键时长缺失或无理由绕行时先说明并调整。通过后交付文字计划，**同一轮继续执行第二阶段工具调用**，不要在总结或“确认后再展示”的邀请处结束。普通可选建议不构成等待理由，无需额外获得首版展示确认。
3. **页面在场，逐步可见**：先确认渲染和目标 `viewId`，默认用 apply_plan 一次提交已核验的完整计划；服务端逐步写入并等待每步真实页面回执，推送进度活动。Agent 用 get_plan_task 长轮询任务，不拆成逐地点调用，不每步截图或短间隔轮询；不能后台录完整份计划后才打开浏览器。最终还要进入播放页并实际开始播放，不能以“保存成功”代替“展示完成”。
4. **后续修改才等待确认**：首次展示成功以后，用户继续调整时先改文字，确认本版后再更新同一行程并展示；“改完直接展示”已包含确认。首次尚未展示时不能套用此等待规则。
5. **结束前自检**：是否已打开且渲染页面？是否在同一页面逐步显示录入？是否收到首版播放开始回执（仅一个地点则核验地图已显示）？未达到时继续执行，不以“可以展示”“需要的话再播放”收尾。只有用户明确只要文字/暂不展示，或缺日期、Key、MCP、浏览器等真实阻塞时才暂停相应步骤，准确说明阻塞和已完成部分。

围绕用户实际脚力、兴趣和时间，制定能执行的景点级旅行计划。主流程：了解需求 → 查天气 → 搜集攻略 → 筛选景点 → 估算时间与强度 → 编排 → 根据反馈调整。

包含两个阶段，也支持用户直接提供已有计划：

- **第一阶段：旅行规划与调整**。按下列流程形成每日计划；直接用 get_status 检查/按需启动服务，再通过页面渲染和连接门槛，并复用状态中的 search.providers 判断搜索源。仅缺所需 Key 或鉴权/配额错误时读取 [Key 申请说明](references/setup.md)。文字规划本身不依赖搜索 Key，缺配置时可继续研究，但不能假装已完成地图地点核验。
- **第二阶段：录入与展示**。通过规划检查后，主动说明“接下来把这版行程放到地图里展示”，直接读取 [MCP 录入与播放](references/mcp-execution.md) 并执行，让用户第一次就能看到展示能力；不再要求用户另说“展示”。新 apply_plan 任务必须带 review，服务端核对每日时间账。用户明确只要文字、暂不展示或不写入应用时尊重其选择。
- **首次展示后的修改**：先在对话中调整计划，等用户确认这一版后再同步应用并展示，不因每条修改意见反复写入、切页或播放。用户说“按这个改并展示”“改完直接播放”等已包含确认，直接执行；用户明确要求边改边展示时沿用其要求。该状态只根据当前会话或用户明确提供的记录判断。
- **已有计划直接录入/展示**：提取已有信息，只补影响录入的关键缺口，不重复旅行需求访谈。

展示时优先使用 Agent **内置的交互浏览器工具**，在服务检查/启动完成后立即打开本地应用并确认页面已渲染和连接就绪，在此之前禁止行程写入，避免默认启动电脑浏览器；无内置浏览器或其无法访问本地服务时再降级为系统浏览器，具体按 MCP 参考执行。MCP 不可用时交付文字计划并说明展示阻塞，配置补齐后继续原计划。

网页素材、预订和视频导出不在本 Skill 的自动执行范围内。

## 1. 分轮了解用户

先承接用户已说的信息，只补会影响规划的缺口。用自然沟通分轮收集，不一上来发全量问卷，不重复问已知项。

- **第一轮，基本背景**：目的地、出发地、日期/天数（是否可调整）、人数与老人小孩情况、喜欢悠闲还是多走多看。日期尚未确定时先帮助缩小范围，不虚构日期或先给一份完整日程。
- **第二轮，针对性补充**：兴趣、必去/不去项；实际连续步行能力、爬坡/台阶限制、午休等需求；已订车票/酒店/预约；自驾或公共交通偏好；每天希望几点出门和结束。已有到离时间、住宿区域和车站/机场也一并承接，未定则在编排前补齐影响排程的部分。
- **不主动询问预算**，不把预算作为开始规划的前置条件。用户主动提出费用约束时尊重它，但不承诺精确控制整趟总价。
- 判断依据是实际能力，不按年龄直接推断能不能爬山，也不因带孩子就默认喜欢某类景点。

例如用户说“苏州去杭州三天，夫妻带7岁孩子，悠闲一点”，先承接这些信息、补具体日期；再逐步了解兴趣、到离时间和休息需要，不重新问出发地、人数或预算。

## 2. 先反馈天气

进入目的地天气研究时读取 [天气来源与判断](references/weather.md)：逐日预报直接调 MCP 的 `get_weather` 工具（坐标或城市名 + 日期范围），官方预警再用固定网页入口核验；不要用 bash/curl 抓天气网页，也不要每次重新筛选网站。

- 给出覆盖出行日期的天气及衣物、雨具、防晒等建议。普通阴天、小雨直接继续规划。
- 例如5天中2–3天暴雨，或有涉及本次旅行区域和时段的有效大风/暴雨等预警：说明影响并与用户确认如何调整，收到决定前不定稿受影响安排。
- 查不到未来日期、查询失败、预警未核验是不同情况，分别说明；不能拿当前预警或季节气候替代未来天气。

## 3. 从攻略建立景点候选池

进入攻略搜集时读取 [资料来源与景点卡片](references/research.md)。**发现景点、了解体验与停留时间优先看小红书、知乎等社交攻略；开放、预约、关闭等限制再到官方核验。**

按用户背景、季节和兴趣搜索，广泛发现后逐步深入。比较亲历体验、合并别名/重复内容，形成“优先考虑、可选、不适合本次”的候选；说明对本次旅行的适配理由，不照搬热门榜、不声称找齐全部景点。

每个入选候选只需景点介绍、建议停留时间范围、位置/区域、体力与天气注意事项、开放预约限制和来源。**规划以景点为单位，路线建议聚焦景点之间；不展开景区内部逐段玩法、打卡路径或多套详细游线。** 内部情况只有影响是否适合、停留多久或是否费力时才简要说明。

## 4. 估算时间和强度

先依据可核验攻略的相近人群停留时间，缺少可靠数据时明确标为规划估算。步行慢、喜欢细看和需要休息分别考虑；不能只将整个景点时间乘大，仍让用户连续走一整天。

`1.3`（较慢/悠闲）、`0.8`（紧凑）等只能作为资料不足时可调整的估算系数，不是年龄公式或保证。仅调整可变游览部分，不压缩开放/预约时段、固定交通、排队和休息。留意攻略时长是否已经包含排队/接驳，避免重复计时。

## 5. 编排每日行程

编排前读取 [排程与输出](references/scheduling.md)。

- 先确定出发地到首站、最终离开点及交通方式；结合距离、已订班次和用户偏好比较，不因某种方式可行就断言它是唯一选项。
- 每日时间需容纳：游览＋交通＋吃饭＋休息＋必要缓冲；涉及入住/退房/寄存也要计入。普通日遵守作息，首末日按到离时间收缩，返程提前结束游玩并留出进站/机场流程时间。
- 在预约、开放、天气、住宿与用户必去约束内按区域组合、减少折返；交通看真实方式与衔接，不用直线距离冒充通行耗时。
- 同时检查时间与体力。排不下就减景点、调整交通或与用户沟通取舍，不能靠擅自提前出门、延后返回硬塞。
- 餐饮、住宿只建议大致区域并预留时间，不主动细化酒店和餐厅商家。

**交付首版或进入录入前，必须实际完成以下检查，并在计划中简要说明结果：**

1. **区域与往返**：先把候选按实际位置组合，比较每日顺序及跨日衔接。相邻景点拆到不同天、同一区域反复进出时，核查是否由用户已订住宿、天气、预约或明确偏好造成；有约束则解释，无依据则重排。不为了“每天都有景点”硬拆，不把必要的住宿返回一律当成错误。地理不清楚时，可在已打开且 ready 的页面上提前 search_places 核验并复用候选，不等计划定稿后才发现位置。
2. **大型景区范围与时长**：明确是门口/周边停留、短线体验、主要景点游览，还是多日游；依据相近人群攻略并核验运营限制。把到景区入口、内部接驳、排队、游览和离开分别计入；时间资料已经包含的部分不重复计。一个地图 POI 或道路导航终点不代表景区能在短时间游完，索道可达也不证明体力轻松。资料不足不能自行把整日游压成几小时。
3. **每日时间账**：确定真实可用窗口；交通＋游览＋用餐休息＋缓冲必须装得下。首末日落实到离交通与行李衔接，按 [排程检查](references/scheduling.md#录入前检查与-review-时间账)填写 review。超时先减项目、重排或解释取舍，不能修改数字凑过检查。
4. **一致性**：文字、review 和将提交的 dates/stops/transport 一致；有关键缺口就保持初稿。播放成功只能证明展示，不能证明现实行程可行。

## 6. 交付与调整

用用户能直接阅读的每日计划表达：日期/时段、景点简短介绍与顺序、建议停留、景点间交通及耗时依据、吃饭休息和返回安排。附天气影响、每日强度、预约提醒、备选和待确认项；提供来源，区分核验事实与估算，不给资料不支持的分钟级精度。

用户反馈后调整，并同步检查后续日程、交通和休息是否仍可行。没有新冲突时不机械重复征求确认。已确定计划保留日期、景点名称与顺序、交通方式。首版文字计划通过§5检查且无关键缺口后，必须同一轮执行§7，不能停下来等待展示确认；首次展示后的修改先等待本版确认，再更新同一个行程并展示，不重复新建。停留、用餐和休息建议保留在文字计划或行程说明中；review 是任务校验参数，不是行程或地点的新字段。

## 7. 将已有计划录入并播放

第二阶段直接使用 [MCP 工具速查与两地点完整调用例](references/mcp-quickstart.md) 中的工具短名和参数；完整计划由 apply_plan 内部创建行程，无需再研究“通过 API 创建新行程”。当前客户端已暴露工具时直接调用，只有命名空间前缀不同时才匹配一次，不重新找服务器、重复发现工具或安装。前置门槛、回执与异常处理见下方执行参考。

读取 [MCP 录入与播放](references/mcp-execution.md)：get_status 一次获取 url/search/views，离线才 ensure_service → 实际浏览器 navigate + snapshot → 核验本次页面 ready/viewId → 提取日期、每日顺序与相邻交通 → 复用有效 candidateId，缺少时搜索核验 → apply_plan 一次提交，服务端逐步可见执行与播放 → get_plan_task 长轮询 → get_trip 和最终 snapshot 核验 → **为每天写入天气**（edit_itinerary 的 `set_weather`：`{op:"set_weather", dayId, weather:{label, low, high, effect}}`；label 如「晴转多云」，low/high 为摄氏气温，effect 从 sun/cloud/overcast/fog/drizzle/rain/heavy-rain/snow/heavy-snow/breeze/wind/storm 中选最接近的）。天气来自§2已核验的预报，逐日对应日期，不凭空编造。任务失败仅 resumable:true 时沿用同 requestId 和相同计划恢复；resumable:false 先核验错误和现有数据，停止自动重试，不重建行程；局部修改保留低层工具。

只在第一版展示或后续版本已确认后开始录入；先确定浏览器和目标 viewId，录入中保留可见联动，让用户看到地点和交通的变化，信息填齐后再播放。保存成功、页面展示成功和播放开始是不同结果，分别按回执报告；显示失败不重复添加数据。

## 常见偏差

| 偏差 | 修正 |
| --- | --- |
| 只按官网宣传或平台热度挑景点 | 看与用户背景相近的真实攻略，再核验官方限制 |
| 正文读不到却声称已看完攻略 | 明示读取缺口，换可访问资料，不编造体验 |
| 普通小雨也反复问是否出行 | 给出调整和携带建议，继续规划 |
| 把饭点和休息排在景点塞满之后 | 在每日时间账里提前占位 |
| 用增加停留时间代替降低步行强度 | 减少景点/连续步行，安排休息或合适交通 |
| 第一版交付文字后就结束或等待确认 | 无关键缺口时必须同一轮执行工具、录入并播放；用户明确只要文字时除外 |
| 用户每提一条修改就重新播放 | 首次展示后先调整文字计划，确认本版后再同步展示 |
