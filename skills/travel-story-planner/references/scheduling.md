# 时间、体力与每日编排

## 排程顺序

1. **确定交通边界**：用户从哪里出发，抵达哪个站/机场及何时到达，最后从哪里、何时离开。已订班次、酒店区域和预约作为固定约束；尚未确定时比较可行方式，说明假设。首站位置要能承接到达交通，不从整天游览开始算。
2. **算每日时间账**：普通日按用户希望出门/返回时间；首日扣除出站、取车/交通、行李与入住等实际所需事项；末日保留退房/寄存、取行李、去车站/机场、候车/安检等。具体预留依据适用运营方规则、行程距离与人员情况，不捏造固定通用分钟数。
3. **提前占位**：将用餐、午休/坐下休息、住宿往返与必要缓冲纳入每日安排，不等景点塞满后再补。不指定具体酒店餐厅，但给出住宿/用餐的大致区域，说明交通便利或顺路的理由。现有住宿作为起终点，不擅自换住处。
4. **按区域组合景点**：在已筛选候选中，优先同区域、相近和顺路的组合，再按开放/闭馆、预约、天气、必去项与体力排序。少折返是优化目标，不能凌驾于这些约束。
5. **核对交通**：区分步行、公共交通、开车、跨城交通。考虑接驳、换乘、等车与出入口；没有实际数据就标估算/待核验，不以直线距离直接换算准确通行时间，不虚构班次/时刻表。
6. **同时检查时间和脚力**：当天总耗时是否在可用窗口内，连续步行和累计负担是否适合用户。需要每隔一段时间坐下的人，不能只增加景点停留，却仍安排长段连续步行；能否休息也要有依据，未核验则注明。
7. **处理冲突**：超时、超体力、天气不适合或预约冲突时，减少可选景点、调整顺序或交通，保留清楚的取舍理由。必去项与硬约束不能同时满足时，向用户说明冲突再调整，不延长用户作息硬塞。

## 时长估算

先使用与当前人群、节奏接近的实际攻略停留范围，并核验是否含排队/接驳。时间系数只辅助估算可变的游览部分，例如把较快记录调整到悠闲节奏；`1.3`、`0.8`不是标准，也不因年龄直接套用。未经证实的结果标注估算，避免看似精确的分钟数。

排队受日期、旺季等影响，不能把别人的单次等待当作保证。固定预约、交通与吃饭休息分别计入，不统一打折，也不重复把已经含在景点停留里的时间再次相加。

路线耗时或开放预约等关键资料不足时，可以给区域顺序和时间块初稿；明确缺口，不把尚未验证的日程说成最终可执行计划。

## 录入前检查与 review 时间账

先确认区域分组、大型景区实际游览范围、停留依据与到离约束，再生成时间账。用户确认计划不代表已经检查过这些条件。相邻景点拆开或跨区返回，记录住宿、天气、预约等实际理由；没有理由就比较合并或调整顺序。往返酒店可能必要，不追求不受约束的最短路线，也不从直线距离推导真实通行耗时。

每个提交的 date 对应 review.days 中恰好一项：

| 字段 | 如何确定 |
| --- | --- |
| availableMinutes | 覆盖当天提交的全部地点与交通的实际可用窗口，遵守用户到离和作息约束。当天含出发站与长途交通时，从出发前开始计并包含该段交通；只有此前交通不在本计划内、当天从抵达点开始时，才能从抵达后计，并在 basis 说明。严禁重复扣减或漏算。 |
| travelMinutes | 窗口内所有交通、换乘及接驳，包含必要住宿往返；等待计在这里或缓冲中一次即可。 |
| visitMinutes | 当天实际游览范围的停留总和；大型景区按核验的游览范围估算，不能只填“到达地点”。 |
| mealRestMinutes | 吃饭、坐下休息及必要入住/寄存等事务时间，分别保留在文字安排里。 |
| bufferMinutes | 未在其他项计入的等候、不确定性和衔接余量。 |
| basis | 可用窗口及到离约束、主要景点范围/时长来源、交通依据、估算与不确定性。不能用“已确认”“合理安排”替代依据；无资料就明确缺口。 |

`review.spatialNotes` 概括区域组合与必要往返理由；不编造已订住宿。所有分钟数为非负整数，每项最多1440，availableMinutes 至少1。每一天满足：

`travelMinutes + visitMinutes + mealRestMinutes + bufferMinutes <= availableMinutes`

MCP 只验证结构、日期覆盖和加法，不能验证来源真伪、游览时长是否充足、区域组合是否最优或道路是否可进入。Agent 必须先完成这些判断，不能靠少填停留/休息、扩大可用窗口通过校验。新任务缺 review、日期不匹配或超时会在写入前拒绝；按错误修正原计划，不用低层工具绕过。review 不自动写成地点的 visitTime/notes 字段。

跨午夜交通按各日实际占用分摊并在 basis 说明，不能漏算或两天重复计入整段时长。

## 对用户的输出

根据任务规模简洁表达，不必机械填满表格。完整计划至少包含：

- 已采用的用户需求、交通/住宿边界和重要假设，已知信息无需反复让用户确认。
- 天气概况、出行适配及穿衣/雨具/防晒建议，预报缺口单独说明。
- 按日期组织的景点顺序、简短介绍、建议停留、景点间交通方式及耗时（来源或估算）、用餐区域和时间、休息与返回安排。
- 每日强度、预约/闭馆注意事项、可选景点/天气替换，以及影响可行性的待确认项。
- 支持关键判断的来源链接，区分事实、攻略体验与规划估算。

可用表格：

| 日期/时段 | 安排与简短介绍 | 停留/交通 | 注意事项 |
| --- | --- | --- | --- |
| 按实际日期填写 | 景点，或用餐/休息/返程 | 用范围或有依据的时长；饭点与交通单独占位 | 强度、预约和待核验项 |

表格只是结构示例，不是要虚构一份已查证行程。用户只问局部调整时只改相关部分，随后检查其对前后衔接和强度的影响。

最终以文字计划保留日期、景点名称与顺序、交通方式。通过以上检查并形成 review 后，且无关键缺口时，同一轮立即进入 [MCP 录入与播放](mcp-execution.md)，除非用户明确只要文字或暂不展示；不得以“还可调整”为由等待展示确认。服务兼容、页面 ready 后，用 apply_plan 一次提交含 review 的计划；服务端逐步写入并等真实页面回执，Agent 长轮询，最后核验数据与播放。复用有效状态和候选；首次展示后的修改先等本版确认，再更新同一行程。按真实回执区分保存、展示与播放。
